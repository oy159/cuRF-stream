# M5：完整组件复查与 2.4 GHz 复验

2026-11-18，接续 [首轮实采记录](m5-live.md)。本轮针对 802.11b 缺项，没有更换 run4 权重，
也没有降低显示置信门限。**M5 计划内的现场定性检查、长测和录像完成**；实验输出位于
`~/dataset/m5_live_v2`。实采准确率未测，识别仍有明显空窗和高未识别比例。

## 先确认输入，再改关联

原计划的 802.11b 依据是频谱形状，不能写成协议解码确认。本轮在 RX2、2440 MHz、61.44 MS/s、
56 MHz 模拟带宽、增益 20 dB 下重新录制 10 秒 IQ：削顶计数为零，峰值约 −7.2 dBFS。
数据没有作为训练样本或实采准确率真值。

独立证据来自两个方向：

- 将 2442 MHz 混频至中心并重采样至 20 MS/s，交给已有的 OnAir 4.2.0 离线 WiFi 接收器，
  读到了该信道信标。只保存观察次数，不保存网络名称、地址或载荷。
  该外部工具同时支持 DSSS 和 OFDM，单凭网络列表不能区分两者，见
  [对应版本的接收器说明](https://github.com/adswill/OnAir/blob/v4.2.0/core/src/wifi/README.md)。
- 自写 `tools/check_dsss_capture.py`，独立于 CNN，对 22 MS/s IQ 的 11 芯片向量投影到 Barker-11，
  每 64 个符号平均能量，再搜索芯片定时与序列方向。同样的一秒观察里，实采相干能量占比峰值为
  0.980，908 个 64 µs 窗超过 0.5；已有 DSSS 仿真对照为 0.987 / 5521 个，OFDM 对照为 0.492 / 0 个。
  这是 DSSS 物理层证据，不是完整的 PLCP / FCS 解码，也不提供分类准确率。

固定输入回放发现：检测结果曾形成约 21 MHz 的完整连通组件，但此前的窄轨迹把它按历史边界分割。
模型只能看到偏移的小片段，例如把应在 2442 MHz 附近的宽信号提取到 2447 MHz 附近。
旧算法可以保住已经找到的载波，却缺少从早期碎片重新发现宽载波的路径。

## 修改范围

保留原来的载波关联和窄轨迹，在满足以下条件时额外复查完整的**当前连通组件**：

- 至少匹配两个原有轨迹，当前宽度至少为 64 个粗信道；默认网格下约 7.68 MHz。
- 新复查组件至少是每个历史组件宽度的三倍，避免把两个已建立的宽载波合为一个。
- 继续复查时，当前与上次组件的频带交并比至少 0.7；关联复查轨迹也使用这个条件。

不跨不连通的检测区域拼接，不用频段规则指定模型类别。复查轨迹不反过来分割原轨迹，
仍受现有重判间隔、请求数、轨迹数及工作区容量约束。运行统计新增 `component_probes`，表示调度的
完整组件复查请求数；原来的跳过计数与原始概率继续保留。

## 复现

```sh
source ~/opt/tensorrt-11.4/env.sh
cmake --build --preset cuda-release
python tools/check_dsss_capture.py \
  --capture /path/to/ism2440.sigmf-meta --frequency 2442e6 \
  --controls ~/dataset/onair --out /path/to/dsss-evidence.json
python tools/run_live_checks.py --bin build/cuda-release/bench/curf_classify \
  --model model/artifacts/s2_run4/export --out ~/dataset/m5_repeat/single \
  --bands ism24 --seconds 300 --max-signals 256 --max-tracks 512 --pending 3 \
  --scratch-mib 128 --max-feed-mib 2048 --display-interval-ms 200 \
  --tune-cache ~/dataset/m5_live_v1/s2_256.tune
```

本轮 2.4 GHz 现场预设恢复到增益 20 dB、检测门限 6 dB，显示策略仍是 M4 冻结配置。
10 秒原始 SigMF 和 packed12 已在本机 `docs/results/m5-v2/capture` 留下经 SHA-256 核对的副本，
远端删除冗余大文件前记录 `archive-locations.json`，为长测保留空间。原有 M4 / M5 v1 证据不删除。
M5 v1 的八份长测 feed 另以 gzip 压缩保留在原目录，本机 `docs/results/m5-v1-archive` 保留原始 feed。
归档时分别核对本机副本、压缩前内容和 gzip 解压内容，均匹配冻结结果的 SHA-256；索引为
远端 `~/dataset/m5_live_v1/feed-archive.json`。可用 `gzip -dc display.feed.gz > /tmp/replay.feed` 恢复回放文件。

## 验证记录

最终 C++ 构建 58/58、Python 55/55 通过。新增完整组件、在途队列、双路大批次 GPU 检查分别为
13 / 368 / 5034 个断言，memcheck 均为 0 errors。
初版关联检查的全阶段 memcheck 在修改 CPU 关联条件后中止，没有将这份未完成日志记为通过；
最终版本重新执行全套 CTest 和针对新增路径的 memcheck。没有更改 GPU 算子实现。

同一份 10 秒 IQ、相同 6 dB 检测门限与相同显示策略的对照结果：

| | 修复前 | 最终修复 |
|---|---:|---:|
| 原始模型结果 | 35221 | 35548 |
| 已命名 / 未识别 | 665 / 34556 | 346 / 35202 |
| 2442 MHz 附近、≥8 MHz 的 WiFi DSSS 推测 | 0 | 114 |
| 上述标签出现的源时间整秒区间 | 0 个 | 0–9，共 10 个 |

新增路径恢复完整宽信号，几何保护也抑制了一部分碎片输出，总命名数没有因此增加。
这是固定输入的行为对照，不是实采准确率评分。最早目标标签出现在 0.055 秒，最后出现在 9.476 秒，
中心约 2441.638 MHz；原始概率保持模型输出。

第一次最终构建的 104 场回归中，标签错误为 0/1726，但种子 33015 的双路 900 MHz 场景出现一次
`skipped_busy`，整轮运行检查判失败；该场 `component_probes=0`。这轮同时在做文件归档传输，
仅凭并发发生不能确认因果。原结果保留在 `m4_final_regression`，不能把它写成全部通过。
归档完成后另开 `m4_final_quiet`，在无并行文件传输、测试或解码任务的条件下复跑，随后再做实采长测。
复跑的 104 场全部通过：命名 1720 条、0 错误，未识别 11497 条（86.99%），调优缓存不变。
每个频段均超过 100 条命名，8 个负控制无命名；丢样、缺口和二级跳过全部为零。
保留一次 busy 的失败结果，复跑通过不代表任意后台负载下都不会跳过。

完整组件复查版本的三个额外频段各做 10 秒短测，运行检查均通过：5.8 GHz 51 条 OFDM，其中 30 条 WiFi 推测；
939 MHz 138 条 OFDM，其中 130 条 LTE 推测；ADS-B 9 条 DF17/18、2 条位置消息、1 架飞机。
这三频段的 300 秒长测仍沿用 M5 v1 记录；本次新版本的长测重点为 2.4 GHz 单路和双路，不混写构建版本。

## 显示处理阻塞的实采复现

低门限、完整 pipe feed 的 300 秒单路试验没有通过：驱动计数全为零、二级容量跳过也为零，
但管线丢失 936706048 个样点、缺口 936574976 个样点，二级 busy / ring 跳过分别为 17494 / 4943。
处理了 1026185 条模型结果；宽带处理 p99 达 113.60 ms。这些失败数据保留在 `long`，
随后开始的双路试验提前停止，没有记作完成的 300 秒试验。

相同硬件、增益、门限、模型和重判间隔，直接写原始 feed 的 30 秒对照为零丢样、零缺口、
零二级跳过，完整记录 98818 条结果。瓶颈来自实时显示处理与同步输出耦合，不能靠扩大 GPU 容量解决。

新增可选 `--display-interval-ms 200`：

- 子进程把每条原始模型结果直接写入 `raw.feed`，包含原始概率；网页处理不再占用接收管线的输出 pipe。
- `tools/live_feed.py` 用有界队列，每个 200 ms 源时间区间保留每条轨迹的最后一次信号观察。
  所有功率瀑布行和 ADS-B 消息逐条保留。模型仍使用原有 6 hop 最小重判间隔，未降为 5 Hz 推理。
- `display.feed` 的元数据与界面明确写出合并间隔。页面计数和该文件中的未识别比例属于**抽样后的显示观察**，
  不能与完整原始记录的计数直接比较。显示增加最多约一个区间的等待，另有实际处理 / 传输耗时；
  C++ 处理延迟不包含这段显示等待。
- 每场 2 GiB 配额均分给原始和显示 feed。原始文件由 Linux `prlimit` 执行硬限制，显示文件逐条写前检查；
  越界会停止接收并保留不完整证据。队列与单行解析也有上限。

原始 / 显示记录保留、接收路隔离、时序、瀑布行、ADS-B 消息、队列上限和文件配额都有测试。
单路和双路各 30 秒短测均通过。最初的 3:1 文件配额与实测体积不符，在 `final_long` 提前停止并保留记录，
没有把它记作完整长测；均分配额后的两场最终试验另存 `acceptance`。

后续按双路观测到的峰值扩展在途队列和请求上限，结果见下文。各轮失败结果保持原值。

## 双路峰值容量

分离显示处理后，`acceptance/ism24` 的单路 300 秒运行检查通过：原始模型结果 1173199 条全部保留，
显示观察 320174 条，其中命名 1924、未识别 318250（99.40%）；宽带处理 p99 / max 为 11.08 / 13.78 ms。
2442 MHz 附近、≥8 MHz 的 DSSS 命名 433 条，十个 30 秒区间均有出现；其中 228 条带 WiFi DSSS 推测，
五个源时间分钟均出现。最长命名空窗 39.22 秒，仍然是间歇识别，不能描述成持续稳定识别。

同一批次双路虽然零丢样，但有 23 次二级 busy，p99 14.96 ms 超过原三个在途窗口约 12.8 ms 的预算。
新增 `--stage2-pending` / `--pending`（默认仍为 3，最多 8）；三槽、八槽均验证了多个窗口同时持有
独立缓存时的结果保序、完整性及数值有限性。八槽、256 请求的 `acceptance_pending8` 双路 300 秒复验
清除了 busy / ring，但发生 8 次请求数上限跳过，仍判失败。

最终双路使用 512 请求 / 1024 轨迹 / 8 个在途窗口，每窗口仍为 128 MiB 工作区。
默认 64 请求 / 256 轨迹 / 3 个在途窗口保持原值。新增 334 个双路交织候选的测试，实际跨越 256 请求；
重排后的 512 个模型参考窗口与 FP32 的 top-1 一致为 512/512，相对 logit 误差 1.30e-3。
调优缓存单独保存为 `~/dataset/m5_live_v2/s2_512.tune`，不改写此前的 256 缓存。

最终双路复现命令（使用新的输出目录）：

```sh
python tools/run_live_checks.py --bin build/cuda-release/bench/curf_classify \
  --model model/artifacts/s2_run4/export --out ~/dataset/m5_repeat/dual \
  --bands ism24 --dual-only --seconds 300 --max-signals 512 --max-tracks 1024 \
  --scratch-mib 128 --pending 8 --max-feed-mib 2048 --display-interval-ms 200 \
  --tune-cache ~/dataset/m5_live_v2/s2_512.tune
```

## 最终验收结果

单路采用 `acceptance/ism24`，双路采用 `acceptance_capacity512/dual_ism24`，各 300 秒。
两场驱动丢失 / 溢出 / 传输错误 / resync / discontinuity、管线丢样 / 缺口及二级 busy / ring /
请求数 / 轨迹数 / 工作区跳过全部为零，`tx_samples=0`。

| 场景 | 请求 / 轨迹 / 在途窗口 | 完整模型记录 | 显示观察：命名 / 未识别 | 未识别比例 | 宽带处理 p99 / max |
|---|---|---:|---:|---:|---|
| RX2 | 256 / 512 / 3 | 1173199 | 1924 / 318250 | 99.40% | 11.08 / 13.78 ms |
| RX1 + RX2 | 512 / 1024 / 8 | 1157863 | 4209 / 372911 | 98.88% | 15.30 / 19.12 ms |

逐文件哈希复核通过：源码快照、二进制、模型、调优缓存、原始和显示 feed 均匹配冻结记录。
原始 `sig` 数量等于 C++ 的 `classified` 和采样器的 `input_signals`；原始与显示的功率行数完全相等，
显示 `sig` 数量等于采样器输出和策略计数，没有通过丢弃原始模型结果降低负载。

双路的 RX2 在目标 2442 MHz 附近显示 653 条 ≥8 MHz DSSS，其中 321 条带 WiFi DSSS 推测；
十个 30 秒区间均出现，最长命名空窗 21.40 秒。RX1 的少量同频输出不能当作负载校准或独立信号真值。
最终双路 GPU 温度峰值 89 °C，功耗峰值 42.17 W，显存峰值 1594 MiB；遥测含启动和结束，
不依据 210–1500 MHz 的全程频率范围推断稳定工作频率或热降频状态。

512 配置再次复用原 M4 的 104 场波形回归，全部运行检查和逐频段门限通过：命名 1720 条、0 错误，
未识别 11495 条（86.98%），高 SNR 载波覆盖 79/91，调优缓存哈希不变。
这是已有仿真波形的回归，没有增加独立验收样本。

另将同一批完整模型 feed 离线套用 200 ms 显示合并：命名 132 条、0 错误，未识别 2586 条（95.14%）。
每频段命名仅 60 / 17 / 30 / 25 条，**未满足每频段 100 条的 M4 样本量门槛**，原报告 `passed=false` 保留。
因此完整显示模式的 M4 回归通过，200 ms 显示配置只完成有限回归和本轮现场定性检查，不能称为新的完整 M4 验收。
短场景在合并后更难积累滞回确认，这个显示召回取舍需要后续用更长的带真值场景评价。
