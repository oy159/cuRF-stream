当前阶段：第二轮 104 场验收通过，首轮失败记录保留。M3 已按功能分成五个提交：

## 固定口径

目标来自 PLAN.md：显示出来的标签错误比例 **<2%**；未识别不算错，单独统计。
本轮把一条有调制族的信号级判决作为一个已命名标签；若还显示了协议推测，也检查协议真值。
调制族错、频率 / 时间匹配不到发射、或协议推测不兼容，均算错；同一条只计一次。
协议推测只验证当前生成器所覆盖的协议，不等同于解码，也不能证明能区分所有同族相似协议。

- 主错误率：错误已命名记录 / 全部已命名记录，同时要求总计和每个 RF 频段都 <2%。
- 未识别比例：未识别记录 /（已命名 + 未识别记录），包括未匹配候选。
- 全部拒识时错误率为 null，不能通过；正式验收还要求每个频段至少 100 条已命名记录。
- 噪声控制场景不能产生已命名记录。丢样、样点缺口、二级跳过、ADC 削顶、未完成运行均不能通过。
- ≥14 dB 的目标载波中，有多少曾得到正确标签另行报告。候选记录的未识别比例不是发射机召回率。

匹配按 RX 隔离，要求实际时间和频率重叠，拒绝相对目标载波包络中心偏移超过
max(5 kHz, 0.25B) 的片段；B 是该载波在源切片中的占用包络，与 SignalStage 的带宽包络语义一致。
跳频 / 变速发射仍须与当前窗口里的真实包在频率和时间上相交，不能只靠长期包络获得匹配。
同时拒绝与瞬时包宽度相差超过四倍的结果。时间交集至少占较短的模型窗 / 包时长的 5%；这是识别窗口，
允许只观察到包的一部分，不要求完整包解码。窗口完全在发射之外仍然算未匹配。
原有 M2/M3 评分默认的 25% 时间门限不变。

## 场景设计

`model/make_room_scene.py` 在 61.44 MS/s 下分块生成 packed12，不把几 GB 的完整场景常驻内存。
源文件来自已有 OnAir 协议仿真与自研 FM 生成器，没有使用天线实采作为准确率真值。
每个 RX 独立产生发射机、信道和噪声；2.4 GHz、5.8 GHz、900 MHz 蜂窝和 2.1 GHz 蜂窝分别调谐。
每种调谐包含对应的 WiFi / BLE / Zigbee 或 LTE 波形，随机选择模式、中心、功率、出现时间和间歇。
发射机的占用包络互不重叠，并留出 250 kHz 保护距离；本轮不覆盖同频碰撞和强邻道压制。
不把 2.4 GHz WiFi 和 900 MHz LTE 放进同一实际 RF 接收带宽。

SNR 分为 0–8、8–14、14–22、22–30 dB；源有小频偏、弱双径，接收路有 IQ 不平衡、直流残余、
白噪声及 12 位量化。真值来自干净源的发射区间，按随机相位循环与启停精确裁剪，包含 RX、
调制族、协议、频率、带宽和源身份。没有模拟完整 AD9361 射频链路，也没有通过硬件发射。

开发集使用源录音 75–87.5%，验收集使用 87.5–100%；它们仍共享同一套干净协议录音，不能
当成全新的协议测试集。场景随机种子分开，开发集从 13001 开始，首轮验收从 23001 开始；
修复后使用新的 33001 起始种子，保留首轮结果。每套另有四个纯噪声场景、四个注入 FM / PSK 的先验外控制场景。
当前控制源是连续广播 FM `fmbc_0` 和 DVB-S 8PSK；运行前检查全部可能源在相应时间切片内有发射。

本轮使用冻结的 run4 模型和自研 FP16 引擎，未把 INT8 路径的结果混入。
策略只看真实分类 feed，不读取真值。阈值比较仅用于开发集；验收运行前冻结配置、代码、
二进制和模型哈希。记录 Python / NumPy / SciPy 版本，保留源代码快照、二进制、权重和逐场景
命令；每个 raw 文件在生成时计算 SHA256。相关模型窗不是独立统计样本，因此不把窗口数量
当作独立试验数来宣称统计置信保证。

## 开发集发现及保护

初始开发检查暴露了两类问题：低 SNR 下一个宽载波被分割成多个局部候选；直流附近的窄候选
有时会被高置信地判为 FSK。模型的高概率不能单独证明提取出的完整载波是可信的。

新增的 `snr_db` 使用模型观察窗未归一化功率、第一级测得的噪声底、PFB 原型滤波器能量增益、
以及局部噪声形状估计。有限提取 FIR 的噪声等效带宽略低于 0.75×输出采样率，使用这个上界
保守估计噪声功率。此值是提取窗 SNR 估计，不是发射机标称 SNR，也不是已校准的硬件绝对量。

新默认策略要求提取窗 SNR ≥10 dB，原始 / 先验内进入置信度 ≥0.90，保持门限 0.85；其他频段
置信门限 0.97。还按频段检查带宽，例如 2.4 GHz 的 FSK 至少 300 kHz、WiFi 频段 OFDM 至少
12 MHz。WiFi OFDM 和宽 DSSS 还要求中心在 5 MHz 信道栅格的 ±500 kHz 内，
避免把载波裙边命名成另一个 WiFi。这些是 v1 演示场景的保守先验，不是对所有无线系统的通用限制。
不满足时保持未识别，原始概率和信号仍可在工程视图检查；滞回不能绕过质量约束。

对 2.4 GHz 的窄 FSK / DSSS 候选增加几何保护：同 RX 最近 80 ms 有 ≥8 MHz 宽候选，
窄候选宽度不超过它的 75%，且频率区间嵌入或间隔不超过宽候选带宽的 10%，则保持未识别。
这些原始宽候选即使没有命名也提供几何证据；保护按源时钟过期，不能跨 RX 使用。
这是对提取碎片的保守拒识，也可能暂时拒绝靠近宽信号的真实窄发射机；没有修复底层候选分裂。

旧的已处理 feed 可按录制策略重放。重新应用新策略时，缺少 SNR 证据的原始记录会保持未识别。
M3 文档中的门限属于当时的验收记录，当前参数以 `tools/policy/default.json` 为准。

四个频段均低于 2%；未识别 2951 条，占 85.54%。≥14 dB 的目标载波中 27/34 曾获正确标签。
策略 SHA256 为 `f320d498ace7c5c87401970c02c99ad58538f89bfb21a534db7a1d6dcd1b5338`。
开发过程保留了失败结果和阈值对比；该次开发结果是
`m4_dev_v3/trial_f320d498ace7.json`，原 `result.json` 是调整前的失败结果。

开发中还修正了两个评分口径：识别允许观察到包的一部分，时间交集门限由 25% 降至 5%；
中心偏差以发射机占用包络为参考，避免把变速 / 跳频包的瞬时中心与跟踪包络混为一谈。

## 复现

在已配置 CUDA / TensorRT 环境的远端主机执行：

```sh
python -m unittest discover -s tests
python tools/run_room_checks.py --split dev \
  --bin build/cuda-release/bench/curf_classify --model model/artifacts/s2_run4/export \
  --src ~/dataset/onair --emissions ~/dataset/ds_v5/emissions.json --out ~/dataset/m4_dev_v3

# 开发集原始 feed 可离线比较配置；不重生成波形，不读验收集
python tools/run_room_checks.py --split dev --rescore --policy trial.json \
  --bin build/cuda-release/bench/curf_classify --model model/artifacts/s2_run4/export \
  --src ~/dataset/onair --emissions ~/dataset/ds_v5/emissions.json --out ~/dataset/m4_dev_v3

# 默认 96 个正场景 + 8 个控制场景，四个 RF 频段
python tools/run_room_checks.py --split acceptance --seed-base 33001 \
  --bin build/cuda-release/bench/curf_classify --model model/artifacts/s2_run4/export \
  --src ~/dataset/onair --emissions ~/dataset/ds_v5/emissions.json --out ~/dataset/m4_acceptance_v2
```

`--resume` 只允许策略、代码、二进制和输入索引哈希都相同。验收集不允许 `--rescore` 更换策略。
结果在 `result.json`，逐场景统计和错误样本在 `progress.json`，真值、原始 / 策略 feed、运行计数
和生成参数保存在各场景目录。开发集失败与阈值比较记录保留，不能把它们称为验收结果。
