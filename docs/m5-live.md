# M5 室内接收试跑

当前状态：五类实采长测、容量修复后的三场补测和录像已完成；运行检查通过，802.11b 定性识别尚未通过，M5 不记为全部完成。
试跑跨 2026-11-17 / 18。M4 已提交为 `ea9620c`、`341d0fd`、`73e50ed`、`acae5cc`，无协作者署名。

## 范围和判据

使用已连接的 OmniCoreSDR、RX2、61.44 MS/s、12 位 IQ、56 MHz 模拟带宽、44 MHz 检测范围和 run4 FP16。
额外运行双 RX 的 2.4 GHz 性能场景。SDR 不创建 TX 流；结果必须有 `tx_samples=0`。
没有把 RX1 接线当作 50 Ω 校准，没有加载旧的噪声形状或杂散表，也没有采集新的训练 / 准确率测试集。

性能与定性识别分开：

- 每个长测至少 300 秒，检查驱动丢失 / 溢出 / 传输错误 / resync / discontinuity，管线丢样 / 缺口和二级 busy / ring / capacity 跳过。
- 保存处理延迟与 GPU 温度、功耗、频率、显存和利用率。模型观察窗时长仍不包含在处理延迟内。
- 标签只是模型加显示策略的输出，不能当成真值或据此给出实采准确率。关注此前确认过的 939 MHz LTE、5.8 GHz WiFi、2.4 GHz 802.11b。
- ADS-B 只显示 CRC 通过的 DF17/18；未收到时如实保留空表，不用仿真飞机替代。
- 长采不逐样本计数 ADC 削顶，不能宣称长采零削顶；只有短 IQ 探针做过直接检查。

`tools/run_live_checks.py` 复用当前 `Hub` / `Handler` / 显示策略提供实时网页，保存包含原始概率的策略 feed，
不保存整个长测的全速 IQ。每场 feed 有容量上限，空间检查保留 3 GiB；超限会停止接收并留下不完整证据。
运行前保存配置、命令、代码、二进制和模型哈希及快照；已有 manifest 的目录不能覆盖。

## 前置检查与参数选择

设备 USB 3.0 在线，RX FIR 关闭。GPU 空闲，内存可用约 11 GiB。独立验证目录原来只编译了文件回放路径；
启用 `CURF_OMNICORE=ON` 后重新构建，C++ 54/54 通过。

最初 2.4 GHz、增益 40 dB、检测门限 6 dB 的 10 秒检查虽然零丢样，却有 4026 次二级容量跳过。
0.5 秒 ADC 探针在 40 / 30 dB 下检测到削顶，自动降至 20 dB 后没有检测到削顶，峰值约 −8.4 dBFS。
20 dB / 6 dB 和关闭 DC guard 的两轮仍有容量跳过；提高检测门限至 12 dB 后，20 dB、10 dB 增益的
两轮 10 秒检查均无跳过。选择更有余量的 10 dB / 12 dB 进入长测。这是检测前端的保守取舍，会漏掉弱候选。

首轮冻结参数如下；当前工具的 5.8 GHz 默认中心已按实测占用调整为 5770 MHz：

| 场景 | 中心频率 | RX | 增益 | 检测门限 |
|---|---:|---|---:|---:|
| 2.4 GHz | 2440 MHz | RX2 | 10 dB | 12 dB |
| 5.8 GHz | 5795 MHz | RX2 | 40 dB | 6 dB |
| 900 MHz | 939 MHz | RX2 | 40 dB | 6 dB |
| ADS-B | 1100 MHz，解调 1090 MHz | RX2 | 45 dB | 6 dB |
| 双路性能 | 2440 MHz | RX1 + RX2 | 10 dB | 12 dB |

M4 的显示参数和 run4 权重保持不变。未用实采结果降低显示置信门限。
所有短测都保留在远端 `~/dataset/m5_live_v1/preflight`，ADC 探针在 `adc_probe`。

## 复现与录像

```sh
source ~/opt/tensorrt-11.4/env.sh
cmake --preset cuda-release -DCURF_OMNICORE=ON -DCMAKE_PREFIX_PATH="$HOME/opt/omnicore/0.8.0"
cmake --build --preset cuda-release
python tools/run_live_checks.py --bin build/cuda-release/bench/curf_classify \
  --model model/artifacts/s2_run4/export --out ~/dataset/m5_live_v1/followup \
  --bands ism24,wlan5 --seconds 300 --dual --revision acae5cc \
  --max-signals 256 --max-tracks 512 --scratch-mib 128 \
  --tune-cache ~/dataset/m5_live_v1/s2_256.tune
```

实时网页默认只绑定远端 `127.0.0.1:8085`。通过 SSH 转发到本机，例如 `8770`，浏览器访问
`http://127.0.0.1:8770/?view=demo`。录制脚本按 manifest 等待对应场景，只有页面明确显示
SDR 实采且 RF / 路数匹配才开始录制；每段前半演示视图、后半工程视图。

录像使用隔离安装的可选 Playwright 与系统 Chrome，不改变 C++ / Python 项目的依赖：

```sh
npm install --prefix /tmp/curf-m5-video playwright
/tmp/curf-m5-video/node_modules/.bin/playwright install ffmpeg
NODE_PATH=/tmp/curf-m5-video/node_modules node tools/record_live_demo.cjs \
  --url http://127.0.0.1:8770/ --out docs/results/m5/video --seconds 20 \
  --manifest /path/to/copied/manifest.json
```

视频、浏览器版本、源类型、频率、路数、截图和错误记录一并保存。源时钟 / 频谱 / 标签均来自实际接收。
文件回放时服务器另加 `playback` 标记，界面显示“SDR 实采回放”，保留原始物理源和录制时的显示判决。
新增 SNR、带宽、信道栅格、邻近宽候选等拒识原因的中文说明，便于检查未识别的原因。

## 容量修复与回归

默认 64 请求 / 256 轨迹 / 32 MiB 工作区不变。新增显式容量参数，最多 256 个请求，IFFT 仍使用
原有有界计划，按速率和剩余空间分块，模型批次可汇合多个 IFFT 批次。容量跳过细分为请求数、
轨迹数和工作区不足；总计保留原字段，不能靠改统计口径通过。

修复配置为 256 请求 / 512 轨迹 / 每 pending 128 MiB 工作区（3 个 pending 共 384 MiB）。
167 个独立粗候选的 GPU 回归覆盖大批次、请求 / 轨迹 / 工作区耗尽，C++ 55/55 通过；
阶段二 memcheck 6573 个断言、3 个用例、0 errors。Python 44/44 通过。

二级调优缓存通过 `--stage2-tune-cache` 接入现有引擎缓存校验，不和第一级缓存混用。
短测首次调优约 14 秒，后续启动约 2 秒。原先逐文件重复调优的 25 场回归片段保留在
`m4_regression` 并明确标为未完成；完整回归复用原 M4 104 场 packed12 波形，另存 `m4_regression_cached`。
这是已有验收波形的回归，不是新独立验收集。

完整回归的 104 场均通过运行检查：已命名 1734 条、错误 3 条（0.17%），四频段分别为
3/740、0/261、0/383、0/350，全部 <2%；未识别 11265 条（86.66%）。调优缓存哈希未改变。
与 M4 原验收的 1741 / 4 有少量差别：本轮大批次引擎重新调优，FP16 执行路径可有数值差异；
没有重写原始概率或把这次回归当作新的独立准确率证据。

| 场景 | 增益 / 检测门限 | 时长 | 命名 / 未识别 | 未识别比例 | 宽带处理 p99 / max |
|---|---|---:|---:|---:|---|

| 5770 MHz RX2 | 40 / 18 dB | 300.000 s | 1738 / 172378 | 99.00% | 6.85 / 9.03 ms |

三场驱动丢失 / 溢出 / 传输错误 / resync / discontinuity、管线丢样 / 缺口、二级 busy / ring /
capacity（包括请求、轨迹、工作区）均为零，`tx_samples=0`。这验证的是**容量扩展与现场检测参数组合**；
没有证明原始 6 dB 门限下的密集候选问题已经解决。2.4 GHz 提高门限到 24 dB 会牺牲弱信号检出，
候选碎片化也仍存在，不能仅靠加大容量把它当作识别问题的修复。

补测 GPU 遥测峰值为 81 °C、41.53 W、834 MiB 显存；整轮含启动 / 场景切换，
SM 频率范围 210–1965 MHz，不把这个范围当成稳定工作频率或独立热降频结论。

定性结果：

- 5.8 GHz 的 1738 条命名均为 OFDM，其中 1558 条显示 WiFi 推测；主要中心 5765.011 MHz，
  带宽约 16.07–16.46 MHz。高未识别比例仍需保留，命名次数不是独立信号数。
- 939 MHz 沿用首轮完整长测，稳定出现约 9 MHz OFDM / LTE 推测；没有用新模型或参数替换这场结果。
- ADS-B 沿用首轮 CRC 解码证据，126 条 DF17/18、43 条位置消息、1 架飞机。
  飞机表 / 地图的实采回放可见 ICAO `780DDA`、呼号 `CSC8842`。
- 2.4 GHz 单路命名为 5317 条 FSK、33 条 DSSS；双路为 9936 条 FSK、105 条 DSSS。
  两场没有已命名且带宽 ≥8 MHz 的 DSSS，不能把这些窄带输出算作 802.11b。
  短测曾出现约 2442 MHz 的宽 DSSS 候选，长测未稳定重现。因此计划中“已确认的 802.11b”这一项仍待解决。
